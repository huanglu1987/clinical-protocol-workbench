# 中文临床试验方案工作包

面向临床开发部门医学经理的 Codex Skill，用于组织中文 CDE 药物临床试验方案的**策略交接、方案撰写、独立审核和获准后的受控修订**。

当前推荐版本：**v0.1.0-preview.4，公开预览版**。默认推荐标准组合安装，共 7 项 Skill；它仍不是独立桌面软件，也不能替代医学、统计、药物警戒、法规、伦理或申办方批准。

## 最简单的安装方法

把下面整段直接发给 Codex：

```text
请安装 clinical-protocol-workbench v0.1.0-preview.4 标准组合：
先使用 $skill-installer，以 git 方式从以下固定链接取得核心 Skill：
https://github.com/huanglu1987/clinical-protocol-workbench/tree/v0.1.0-preview.4/skills/clinical-protocol-workbench
然后运行实际安装目录内的 scripts/install_bundle.py，使用默认 standard 档位。
这次安装请求包括其固定清单中的 6 项外部 Skill。已有同名目录先核验：
版本一致则跳过；有冲突请列明，不覆盖、不自动升级。
完成后运行 --check，报告 7 项 Skill 的结果及运行库/Word 等环境缺口。
告诉我下一条消息如何调用。
```

安装成功后，从下一条消息开始直接说：

```text
请使用 $clinical-protocol-workbench，根据我提供的资料撰写一份中文 CDE 临床试验方案内部工作初稿。
```

或者：

```text
请使用 $clinical-protocol-workbench，审核这份方案。先只输出问题清单和修改计划，不修改原文件。
```

标准组合会一起安装工作台、两项策略、审核、论文检索、数据库检索和引文管理 Skill。仅把核心链接交给普通安装器仍只安装核心；必须执行上面完整提示或组合脚本，才能补齐其余 6 项。安装不上传项目资料，不安装 Microsoft Word 或 Python 运行库，也不自动取得数据库授权。详细说明、核心档位、升级和冲突处理见 [组合安装指南](docs/INSTALLATION.md)。

## 它解决什么问题

方案撰写的难点不是“生成更多文字”，而是避免把不同来源混成研究事实。这个工作包先区分四类内容：

- **项目事实**：来自明确指定的 IB、研究报告、产品资料和当前方案；
- **设计决定**：已由有权角色确认的剂量、样本量、终点、访视等研究口径；
- **外部证据**：法规、指南、登记研究、公开审评和文献，用于支持、质疑或提出选项；
- **模板与既往方案**：只提供结构、文风和版式，不能把其他项目参数带进来。

每个候选建议先记为 `PROP-*`，未决问题记为 `TBD-*`；只有内容、适用条件和真实确认记录都清楚时，才成为可进入正文的 `DEC-*`。因此，资料不充分时得到的是带明确缺口的工作稿，而不是看起来完整但参数被猜出来的方案。

完整工作原理、工具调用关系和失败边界见[工具与工作原理](docs/TOOLS_AND_ARCHITECTURE.md)。

## 两个模式怎么选

| 你的实际目标 | 使用方式 | 主要交付物 |
| --- | --- | --- |
| 产品处于方案前策略阶段 | 撰写模式的“策略/候选 Synopsis”入口 | 候选路径、依据、设计问题和待确认项 |
| 已有确认的设计或 Synopsis，要形成完整方案 | 撰写模式的“直接起草”入口 | DOCX 工作初稿、控制表、来源/TBD/冲突清单 |
| 资料不足，但要先推进框架 | 撰写模式的“占位工作稿”入口 | 目录、可起草章节、带编号 TBD 和补充资料清单 |
| 已有方案，需要全面核查 | 审核模式 | 覆盖范围、问题清单、证据/算式、修改计划 |
| 已批准具体问题的处理方式 | 审核模式的“受控修订”阶段 | 保留原审阅历史的新 DOCX 副本及分层验证记录 |

如果同一项目同时需要撰写和审核，先完成并冻结初稿，再在新的独立任务中审核。起草者的自检不能冒充独立审核。

## 使用前准备

建议为每个研究建立独立目录，并让智能体只在该目录中工作：

```text
项目目录/
  AGENTS.md          推荐：协作规则和项目控制表位置
  01_输入原件/       只读：IB、研究报告、确认版 Synopsis、公司模板等
  02_外部依据/       法规、指南、全文文献、登记研究和公开审评资料
  03_工作记录/       项目控制表、来源哈希、决定、TBD、冲突和影响图
  04_输出版本/       每轮新建文件，禁止覆盖输入原件
```

建议多轮撰写前建立项目 `AGENTS.md`，但没有它也能使用工作台。已有文件先合并规则，不能覆盖；具体内容和随包模板见 [项目规则说明](docs/PROJECT_AGENTS.md)。完整研究参数与确认记录统一放在项目控制表。

开始时至少告诉智能体：

1. 本轮要策略、完整撰写、占位工作稿还是审核；
2. 哪些文件是项目事实源，哪个是方案模板，哪些只作参考；
3. 哪些研究设计已经确认，确认记录在哪里；
4. 开发地区及产品的给药途径、起效部位、分子类型和适应症；
5. 是否允许联网查找外部证据；
6. 输出目录和本轮禁止执行的动作。

## 皮肤科专业模块

工作包按产品特征选择专业模块，而不是看到疾病名就自动套用：

- [oral-derm-clinical-strategy](https://github.com/huanglu1987/oral-derm-clinical-strategy)：口服小分子，覆盖皮肤、毛发、浅表真菌、疣及相关皮肤感染策略。
- [topical-clinical-strategy](https://github.com/huanglu1987/Topical-Clinical-Strategy-Skill)：局部起效外用小分子，覆盖乳膏、凝胶、软膏、洗剂、喷雾、泡沫和成膜制剂等。

注射生物制剂、经皮系统递送贴剂、细胞/基因或器械主导产品不强行套用这两个模块。通用资料整理和已确认内容起草仍可继续，但必须披露专业覆盖缺口。

固定依赖版本：

- 口服：`b927d7d98283d489ab2661cd9551d0d4068cda37`；
- 外用：`7edded14ad8bbb32a17e8ce2590efa735ff73c8c`。

具体安装与核验见[工具与工作原理中的依赖章节](docs/TOOLS_AND_ARCHITECTURE.md#7-专业策略-skill-如何安装和核验)。两项上游固定树在核查时均未发现 LICENSE；本仓库只保存链接、版本和文件指纹，没有复制上游正文。

## 交付验收的基本原则

医学经理不要只看“文件是否生成”。每次交付至少应有：

- 输入文件、输出文件及 SHA-256；
- 每份来源的角色和允许用途；
- 当前有效设计决定及真实确认记录；
- 未关闭的 TBD、冲突及受影响章节；
- 本轮实际完成的检查和明确未执行的检查；
- 需要医学、统计、药物警戒、法规、运营或其他角色确认的事项。

以下状态不能互相替代：

```text
内容已生成
  ≠ Word 结构检查通过
  ≠ Microsoft Word 实际渲染并逐页检查通过
  ≠ 医学/统计/法规专业批准
  ≠ 可递交
```

## 当前边界

- 当前是公开预览版；完整新方案 DOCX 的端到端真实项目撰写试点尚未完成。
- Windows Word 实机尚未验证；现代批注、移动/属性修订和复杂 OOXML 不在实验 worker 的支持范围。
- 工作包不自动批准剂量、访视、终点、样本量、统计参数、阈值或版本日期。
- 外部证据必须回到适用地区的现行原始来源；固定文件指纹不证明法规时效或临床正确性。
- 工作包本身没有后台服务、遥测或自动发布入口；使用 Codex、外部检索或云端工具时，仍受相应服务和组织的数据政策约束。

## 版本、升级与卸载

[v0.1.0-preview.4 Release](https://github.com/huanglu1987/clinical-protocol-workbench/releases/tag/v0.1.0-preview.4)提供源码 ZIP、文件 SHA-256 清单和发行验证记录。

安装器默认不覆盖同名目录。升级前应将旧目录移到 Codex skills 根目录之外的备份位置，记录旧 tag 和正在使用该版本的项目；再按新 tag 安装。回退时移走新版并恢复完整旧目录，不要合并两个版本。

卸载时，只移走实际安装目录中的 `clinical-protocol-workbench` 文件夹；不要删除整个 skills 根目录。项目输入、输出和外部专业 Skill 不会自动删除。
